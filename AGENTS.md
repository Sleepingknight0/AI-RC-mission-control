# AICL Mission Control Repository Instructions

## Mission

Build a Windows-first, single-operator, enterprise-grade AI CLI mission-control application. Codex owns all Prototype 0 implementation, frontend work, self-audits, remediation, and final integration. Grok and Claude are optional post-prototype reviewers and never block a Prototype 0 milestone.

## Read order

Before changing code, read:

1. `docs/00-PROTOTYPE-0-SCOPE.md`
2. `docs/01-ARCHITECTURE-DECISIONS.md`
3. `docs/05-IMPLEMENTATION-STATUS.md`
4. The active task prompt
5. Relevant sections of `docs/spec/AICL-MISSION-CONTROL-SPEC-V2.2.md`

Do not load or implement the entire long-form specification when the current milestone does not require it.

## Source of truth

Use this precedence:

1. Measured behavior and schemas generated by the installed provider binary
2. Prototype scope and accepted architecture decisions
3. Tests and database constraints
4. This file and the active task prompt
5. Long-form specification
6. Unverified assumptions or AI suggestions

Never invent Codex app-server method names. Generate and inspect schemas from the installed `codex` binary.

## Non-negotiable architecture

- TypeScript strict mode.
- React + Vite for the web application.
- Core and Connector are separate processes, even on one Windows host.
- Frontend imports normalized protocol types only. It must never receive raw provider events.
- Keep Session, Runtime, Turn, Connection, Command, Approval, and Event as distinct concepts.
- SQLite WAL is the baseline authoritative store; Connector journal is a separate SQLite file.
- Durable events commit before broadcast.
- Token and output deltas are ephemeral, coalesced, and never persisted one token per transaction.
- `last_event_seq` and resource revisions are separate counters.
- Approval compare-and-set uses the approval row, runtime generation, turn identity, state, and expiry. It does not depend on a global session revision.
- One executing Turn per Session. No dormant `queued` Turn state in the prototype.
- Connector restart means the old provider runtime is lost. Do not implement stdio or SDK process reattach.
- Ambiguous crash outcomes become `outcome_unknown`. Never auto-resubmit a prompt with possible side effects.
- Every client mutation has a stable `commandId` and duplicate-payload check.
- No unrestricted remote shell endpoint.
- Enforce project-root allowlists and canonical path checks.
- Large diffs and payloads use an artifact endpoint rather than exceeding the WebSocket envelope limit.

## Prototype discipline

- Execute only the first incomplete milestone in `docs/05-IMPLEMENTATION-STATUS.md` unless the user names a specific milestone.
- Produce the smallest end-to-end slice that proves the milestone.
- Do not add Claude provider integration, PTY fallback, multi-user features, cloud control plane, updater, or worktrees during Prototype 0.
- Prefer observable behavior over infrastructure completeness.
- Update `docs/05-IMPLEMENTATION-STATUS.md`, `docs/06-HANDOFF-LOG.md`, and `docs/EXECUTION-PLAN.md` after each milestone.

## Component boundaries

- `apps/web` may import `packages/protocol`, `packages/domain` read models, and UI packages.
- `apps/web` may not import provider adapters or database code.
- `apps/core` owns HTTP/WSS, command acceptance, authoritative SQLite state, event replay, and projections.
- `apps/core` may not access arbitrary project files.
- `apps/connector` owns provider processes, project filesystem access, runtime supervision, and its journal.
- Connector never opens or mutates the Core database.
- Provider adapters never import web code.

## Coding standards

- Use explicit types at process and protocol boundaries.
- Validate external input with generated JSON Schema or Zod-compatible validators.
- Prefer small modules with one responsibility.
- Avoid hidden global state and magic retry loops.
- Every retry must state whether the operation is safe to repeat.
- Errors crossing the protocol boundary require stable codes and structured details.
- Do not swallow exceptions. Classify, log, and surface them.
- Do not log secrets, full credentials, or raw traces by default.

## Testing requirements

For each milestone, add tests at the lowest useful level and run all affected checks. At minimum verify:

- protocol validation
- state transition guards
- database constraints
- duplicate command behavior
- browser refresh/replay behavior when applicable
- provider event normalization
- no raw provider event leakage
- Windows process termination semantics when applicable

Record exact commands and results in the handoff log.

## Git and agent collaboration

- Do not push, force-reset, rewrite history, or delete user work.
- Do not commit unless the active task explicitly requests commits.
- Only one agent may own a file area at a time.
- Codex is the sole Prototype 0 implementation and integration authority.
- After Prototype 0, optional Grok/Claude feedback is advisory; Codex accepts only findings supported by measurements, tests, and accepted decisions.
- Reviews must include file paths, evidence, severity, and a concrete remediation.

## Completion report

At the end of a task, report:

1. Milestone completed or blocked
2. Files changed
3. Commands and tests run
4. Observable demo path
5. Known limitations and uncertain outcomes
6. Next single milestone
