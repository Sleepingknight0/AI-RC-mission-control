# M10.1 Provider Visibility and Disabled-Provider Optimization

## Outcome

The normal Mobile AI Accounts drawer now shows enabled providers only. This
machine's durable active set is Antigravity CLI, Claude Code, Cursor Agent, Grok
Build, and OpenAI Codex. The available/disabled set is Aider, Amazon Q Developer
CLI, Amp, Cline CLI, Continue CLI, Gemini CLI, GitHub Copilot CLI, Kilo Code,
OpenCode, and Qwen Code. The registry contains no separate CrossCode identity,
so the operator's spoken CrossCode resolves to Claude Code without an ID rename.

## Persistence and authority

Each existing `provider.json.enabled` field remains the single durable source of
provider visibility. The browser sends a normalized `provider.enablement.set`
command with stable `commandId`, expected state, and desired state. Core applies
preconditions, records command/audit/result state in schema-15 SQLite, and
relays the command to Connector. Connector deduplicates through its journal,
validates exact provider identity and expected state, then atomically replaces
the bounded manifest. The browser never edits registry files.

This preference does not create provider authority. Enabled providers still
need current installation, authentication, compatibility, account, model, and
Session capability evidence. Account/Session isolation, settings CAS, approval
CAS, runtime-generation fencing, exact account routing, no prompt replay, and
inventory-only behavior remain unchanged.

## Disabled-provider work

Disabled inventory reads the manifest and counts bounded immediate account
directories so the operator can discover and recover stored providers. It does
not probe PATH/executable installation, read account profiles or auth markers,
poll models/usage, list native Sessions, activate remote control, create/resume
Sessions, publish account capability authority, or launch a provider process.
Inventory refresh is event-driven at Connector startup/reconnect and explicit
refresh/enablement actions; there is no recurring provider polling loop.

After a disabled-state application restart, process matching across all ten
disabled manifests found zero provider processes and the isolated Connector had
zero child processes. A three-second repeat observation remained zero/zero.

## Known limitations and next milestone

Disabled providers still incur the intentional lightweight manifest read and
account-directory count needed for provider management. The measurement proves
no persistent disabled-provider process or Connector child and code inspection
finds no recurring provider polling; it is not a system-wide CPU/ETW trace.

The next single milestone is M8.5 real second-device acceptance only if the
operator removes its deferral; otherwise the operator should define the next
post-M10 milestone.
