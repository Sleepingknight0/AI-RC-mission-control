## Verdict

review found 12 reproducible or directly traceable defects: 6 High, 5 Medium,
and 1 Low. No remediation was implemented in M6.1; accepted findings belong to

## Findings

### CR-01 — Connector outbox can replay causal events out of order

- **Severity:** High
- **Affected:** `apps/connector/src/journal.ts:135-174`,
  `apps/connector/migrations/001_initial.sql:16-28` (`enqueue`,
  `pendingEvents`); downstream `apps/core/src/store.ts:603-650,1076-1337`.
- **Reproduction:** Enqueue 100 pairs of
  `connector.turn.message.completed` followed by `connector.turn.completed`
  without acknowledging, then reopen/read `pendingEvents()`.
- **Evidence:** The fault probe returned 49 of 100 pairs with the terminal event
  before its completed message. `created_at` has millisecond precision and the
  tie-breaker is a random UUID (`source_event_id`).
- **Violated invariant:** Durable provider events must reach Core in their
  original causal order, including message-before-Turn and
  begin/chunk/complete ordering.
- **Remediation:** Add a monotonic journal sequence (for example an
  `INTEGER PRIMARY KEY AUTOINCREMENT`) and replay strictly by that sequence.
- **Regression test:** Freeze the clock, enqueue same-millisecond causal event
  chains, restart Connector, and assert exact envelope order plus correct final
  message, activity, file-change, and artifact projections.

### CR-02 — A Core crash can orphan a committed Turn before dispatch

- **Severity:** High
- **Affected:** `apps/core/src/server.ts:314-362` (`turn.submit`),
  `apps/core/src/store.ts:407-537` (`acceptTurn`, `markDispatched`), and
  `apps/core/src/store.ts:359-364` (`activeSnapshots`).
- **Reproduction:** Commit `acceptTurn`, terminate Core before
  `markDispatched`/`sendConnector`, reopen the database, then reconnect the
  same ready Runtime.
- **Evidence:** The probe reconstructed `activeTurnId = gap-turn` and
  `turnStatus = running`; runtime reconciliation produced no event. Retrying
  the same command ID only returns the stored `command.accepted` result.
- **Violated invariant:** A durably accepted side-effecting command must either
  have durable dispatch ownership or converge to an explicit uncertain outcome;
  it must not remain silently running forever.
- **Remediation:** Introduce a durable Core dispatch outbox and Connector receipt
  inventory. Reconcile committed-but-unreceipted dispatches without blind prompt
  replay; ambiguous delivery must become `outcome_unknown`.
- **Regression test:** Crash after accept commit, after dispatch marking, after
  socket write, and before Connector inbox commit. Assert convergence and never
  more than one provider dispatch.

### CR-03 — Side-effecting RPC timeout is recorded as deterministic failure

- **Severity:** High
- **Affected:** `apps/connector/src/codex/rpc-process.ts:38-52`
  (`RpcRequestBroker.request`), `apps/connector/src/codex/adapter.ts:268-292`
  (`startTurn`), `apps/connector/src/client.ts:305-326` (`handleCommand`).
- **Reproduction:** Let the provider accept `turn/start` but withhold its RPC
  response until the broker timeout while provider work continues.
- **Evidence:** Timeout rejects a plain `Error`. Only `ProviderLostError` maps
  to uncertainty, so Connector emits `connector.turn.failed` with
  `PROVIDER_REJECTED` and returns Runtime to `ready`.
- **Violated invariant:** Once a side-effecting dispatch may have crossed the
  provider boundary, timeout cannot prove rejection and must not be reported as
  a safe deterministic failure.
- **Remediation:** Use typed timeout errors containing method and dispatch phase.
  Fence/terminate the Runtime and emit `outcome_unknown` for side-effecting RPC
  timeouts; reserve `failed` for explicit provider rejection.
- **Regression test:** Fake an accepted request with no response, then assert a
  lost Runtime, one `outcome_unknown`, and rejection of a second normal dispatch.

### CR-04 — Provider respawn reuses a lost Runtime identity and generation

- **Severity:** High
- **Affected:** `apps/connector/src/client.ts:67-83,213-326`,
  `apps/connector/src/codex/adapter.ts:352-371,726-743`,
  `apps/core/src/store.ts:1378-1393,1656-1692`, and
  `apps/core/test/real-codex.e2e.test.ts:130-154`.
- **Reproduction:** Kill Codex during a Turn, wait for Runtime `lost`, then send
  a new `turn.submit` without restarting Connector.
- **Evidence:** Connector clears `providerLost`, the adapter spawns a new Codex
  process, and the real-provider test accepts the new Turn without asserting a
  changed Runtime. Journal Runtime ID/generation are immutable. Core schema also
  uses Runtime ID as the primary key, so it cannot represent the same ID at a
  later generation despite the `(id, generation)` foreign key.
- **Violated invariant:** A new provider process/client is a new Runtime
  generation; stale events and approvals must remain fenced from it.
- **Remediation:** Require an explicit recovery/resume command, rotate Runtime
  identity/generation before provider respawn, and reject ordinary submits while
  the current Runtime is lost. Do not replay the old prompt.
- **Regression test:** Kill provider, verify normal submit rejection, explicitly
  resume with a new Runtime identity/generation, and reject all old events and
  approval decisions.

### CR-05 — Connector channel loss is treated as process loss

- **Severity:** High
- **Affected:** `apps/core/src/server.ts:729-759`
  (`scheduleConnectorLoss`, `attachConnector`) and
  `apps/core/src/store.ts:1396-1397,1819-1888` (`markRuntimeLost`).
- **Reproduction:** Start a Turn, close only the Connector WebSocket longer than
  the 750 ms grace, then reconnect with the same Connector ID, boot ID, Runtime
  ID, and generation.
- **Evidence:** The probe emitted `turn.outcome_unknown`; the same-process
  reconnect retained that terminal state even though process identity matched.
- **Violated invariant:** A transport interruption while the Connector process
  survives must preserve Runtime identity and allow journal replay. Only lost
  process ownership should make the outcome unknown.
- **Remediation:** Model disconnected/degraded channel state separately and use
  a boot/runtime ownership lease in `connector.hello`. Same-identity reconnect
  cancels channel-loss escalation; changed/expired ownership triggers loss.
- **Regression test:** Compare a same-boot outage beyond grace with an actual
  new-boot restart and assert different recovery outcomes.

### CR-06 — Core startup does not reconcile ownerless executing Turns

- **Severity:** High
- **Affected:** `apps/core/src/server.ts:77-90,729-738`,
  `apps/core/src/store.ts:347-364` (`latestRuntime`, `activeSnapshots`).
- **Reproduction:** Stop Core and Connector before the live disconnect timer
  runs, restart only Core, and inspect the persisted Session after the expected
  ownership deadline.
- **Evidence:** `latestRuntime()` is loaded, but `activeSnapshots()` is unused
  and no startup lease/reconciliation timer is scheduled. Loss handling exists
  only for a Connector socket that closes in the current Core process.
- **Violated invariant:** On restart, every executing Turn must regain verified
  ownership or converge to lost/`outcome_unknown`; it cannot block its Session
  indefinitely.
- **Remediation:** Rebuild ownership deadlines at Core startup. Cancel only when
  matching Connector inventory proves ownership; otherwise mark the Runtime
  lost, invalidate approvals, and terminalize the Turn as uncertain.
- **Regression test:** Crash both processes, restart Core alone, advance the
  lease deadline, and assert exactly one durable uncertainty transition.

### CR-07 — One provider can receive concurrent Turns from multiple Sessions

- **Severity:** Medium
- **Affected:** `apps/core/src/server.ts:314-362`,
  `apps/core/src/store.ts:425-473`, and
  `apps/connector/src/codex/adapter.ts:186-204,266-292`.
- **Reproduction:** With one Connector/Runtime, submit simultaneously to two
  idle Sessions.
- **Evidence:** Core enforces one running Turn per Session, not per Runtime, and
  accepts both. `CodexProvider` has one global `#active`; one command fails late.
  On cold start, both commands can pass the pre-await `#active` check before
  either assigns it.
- **Violated invariant:** Accepted work must match actual provider concurrency;
  a command cannot be durably accepted if its Runtime cannot own it.
- **Remediation:** Either allocate a provider Runtime per Session or enforce one
  executing Turn per Runtime transactionally before acceptance.
- **Regression test:** Submit to two Sessions concurrently and assert separate
  Runtime ownership or a deterministic pre-acceptance `RUNTIME_BUSY` rejection.

### CR-08 — Approval expiry is passive and can leave stale actionable UI

- **Severity:** Medium
- **Affected:** `apps/core/src/store.ts:882-987` (`resolveApproval`) and
  `apps/web/src/App.tsx:708-711,1174-1208` (`pendingApprovals`).
- **Reproduction:** Receive an approval, do not click it, and wait beyond
  `expiresAt` while Core and browser remain connected.
- **Evidence:** Expiry is checked only inside a later resolution attempt. The
  projection remains `pending`; Web filters only by state and keeps both action
  buttons enabled.
- **Violated invariant:** Expired authority must stop appearing actionable and
  must resolve the waiting provider path consistently, including after restart.
- **Remediation:** Add a durable Core expiry reconciler, rebuild timers on
  restart, transition exactly once, and send a safely fenced provider decline
  when delivery is still provable.
- **Regression test:** Let approval expire without browser action, repeat across
  Core restart, and assert one `approval.expired` event and no usable decision.

### CR-09 — Rejected approval commands can leave the browser permanently locked

- **Severity:** Medium
- **Affected:** `apps/web/src/App.tsx:248-250,345-357,601-624`
  (`approvalCommandsRef`, `resolveApproval`).
- **Reproduction:** Submit an approval decision that Core rejects without also
  emitting an approval state event, such as a stale expected revision.
- **Evidence:** The map is written with key `approvalId:decision` but
  `command.rejected` reads it by `commandId`; lookup always misses and
  `resolving` retains the approval ID.
- **Violated invariant:** Every terminal command response must release local UI
  in-flight state and return control to the authoritative projection.
- **Remediation:** Index the correlation map by command ID (or maintain both
  indices) and clear resolving state for every terminal response.
- **Regression test:** Reject a decision without a follow-up approval event and
  assert that controls re-enable and retry uses the intended idempotency key.

### CR-10 — Connector command delivery errors are not durable Core outcomes

- **Severity:** Medium
- **Affected:** `apps/connector/src/client.ts:241-301`,
  `apps/core/src/server.ts:610-624`, and
  `apps/core/src/store.ts:1374-1375` (`recordConnectorNotice`).
- **Reproduction:** Make provider interrupt or approval resolution throw after
  Core has accepted the command, then refresh/reconnect the browser and resend
  the same command ID.
- **Evidence:** Connector persists `outcome_unknown`, but Core records only the
  source receipt and broadcasts an ephemeral `protocol.error`. It does not
  transition the durable command or related projection; duplicate lookup still
  returns the original accepted result.
- **Violated invariant:** An accepted control command must have an authoritative,
  reconnect-safe terminal result, especially when provider delivery is unknown.
- **Remediation:** Persist Connector command outcomes in Core, reconcile the
  affected Turn/approval, and return the current terminal result on duplicate.
- **Regression test:** Inject delivery failure, reconnect a browser, and assert
  durable uncertain state and idempotent duplicate behavior without redispatch.

### CR-11 — Reconstructed timeline does not preserve cross-type chronology

- **Severity:** Medium
- **Affected:** `apps/web/src/state.ts:257-300` (`buildTimeline`) and Core
  snapshot projections assembled in `apps/core/src/store.ts:203-294`.
- **Reproduction:** Produce a Turn with a command activity before a final
  assistant message, then compare live event order with the reconstructed UI
  after refresh.
- **Evidence:** Snapshot rows do not expose a common durable sequence. Web emits
  all messages, then all activities, then all file changes for each Turn, so
  resource type overrides causal chronology.
- **Violated invariant:** Reconnect reconstruction must not change the observable
  order of normalized durable events.
- **Remediation:** Expose a shared display sequence/timestamp from durable event
  projection and merge timeline entries by it with a stable tie-breaker.
- **Regression test:** Interleave message/activity/file-change events, reload,
  and assert item identity and order match the live durable sequence.

### CR-12 — Command lifecycle values and transitions lack database enforcement

- **Severity:** Low
- **Affected:** `apps/core/migrations/001_initial.sql:27-40` (`commands`) and
  `apps/core/src/store.ts:529-537,1629-1653` (`markDispatched`,
  `#insertCommand`).
- **Reproduction:** Insert an invalid command state through the database API or
  call dispatch marking after a command has already reached a terminal state.
- **Evidence:** `commands.state` and `command_type` are unconstrained text, and
  `markDispatched` does not inspect the update's affected-row count.
- **Violated invariant:** SQLite is the authoritative state machine and must
  reject invalid lifecycle values/transitions rather than silently no-op.
- **Remediation:** Add enum `CHECK` constraints in a migration and centralize
  transitions with expected-state predicates whose results are verified before
  external dispatch.
- **Regression test:** Assert invalid raw values fail and every illegal command
  transition returns a failure before any Connector send.

## Verified Controls and Falsified Hypotheses

- Concurrent duplicate command IDs with identical payloads converge to one
  mutation; mismatched payload reuse is rejected.
- SQLite writer serialization, WAL configuration, and the partial unique index
  for one running Turn per Session behave as tested.
- Durable events commit before browser broadcast, and browser replay deduplicates
  by Session-local sequence.
- Approval compare-and-set includes approval revision, Turn, Runtime generation,
  provider correlation, expiry-at-click, and device attribution; two-tab races
  produce exactly one winner.
- Ordered artifact ingestion validates scope, chunk count, byte length, and
  SHA-256. CR-01 can violate transport ordering, but no independent artifact
  integrity bypass was found in M6.1.
- Provider exit invalidates pending approvals and records
  `turn.outcome_unknown`; no automatic prompt replay exists in Connector inbox
  recovery.
- The suspected snapshot-to-live subscription race was falsified: after the
  awaited snapshot load, subscription registration and replay are synchronous
  in the same event-loop turn.
- The Windows provider tree termination regression passed.
