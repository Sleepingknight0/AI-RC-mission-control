## Non-Negotiable Architecture Invariants

Preserve all existing accepted invariants, including:

- TypeScript strict mode.
- React + Vite for the web application.
- Core and Connector remain separate processes.
- Frontend consumes normalized protocol types only.
- Raw provider events must never reach the frontend.
- Session, Runtime, Turn, Connection, Command, Approval, Artifact, and Event remain distinct concepts.
- SQLite WAL is the authoritative Core store; Connector journal is separate.
- Durable events commit before broadcast.
- Token and output deltas are ephemeral and coalesced; never persist one token per transaction.
- `last_event_seq` is separate from resource revisions.
- Approval resolution uses compare-and-set on the approval resource, not a global Session revision.
- Runtime ID and generation fence provider-bound decisions.
- One executing Turn per Session; no dormant `queued` Turn state.
- Connector restart means the old provider runtime is lost.
- Do not implement stdio or SDK process reattach.
- Ambiguous provider failure becomes `outcome_unknown`.
- Never auto-resubmit a prompt that may have produced side effects.
- Every client mutation has a stable `commandId` and duplicate-payload validation.
- No unrestricted remote-shell endpoint.
- Project roots, canonical paths, symlinks, and Windows junctions require explicit boundary validation.
- Large diffs and payloads use artifact transport rather than exceeding WebSocket limits.
- Do not weaken validation, constraints, or tests to make checks pass.

Priority order when requirements conflict:

1. side-effect safety
2. data integrity and recovery correctness
3. provider compatibility based on measured behavior
4. protocol and authorization boundaries
5. functional completeness
6. usability and accessibility
7. performance
8. visual polish

## M4 — Activity, Approval, Interrupt, and Diff Completion

When M4 remains incomplete, finish the existing protocol/database foundation rather than creating a parallel implementation.

Required behavior:

- normalize command/tool started, bounded output deltas, completion, failure, decline, and interrupt
- normalize file changes and diff metadata
- keep raw provider identifiers internal except for opaque Connector correlation
- persist authoritative activity, file-change, approval, and artifact state
- expose typed normalized data through Core WebSocket and snapshot/replay paths
- preserve ordering between durable boundaries and ephemeral output batches
- invalidate pending approvals when the owning runtime is lost

Approval compare-and-set must validate at least:

- approval is still pending
- expected approval revision matches
- runtime ID and generation match
- Turn identity and valid Turn state match
- provider request correlation matches Connector state
- approval has not expired
- duplicate `commandId` returns the prior result and does not dispatch twice

Large diff requirements:

- enforce configured inline thresholds
- store oversized content as artifacts
- include SHA-256, byte length, media type, and stable opaque identity
- authenticate retrieval
- support bounded or range-capable retrieval where specified
- prevent path traversal and arbitrary local path exposure
- reject corrupted or mismatched content

Required tests include simultaneous approval from two tabs, approval after expiry, approval after generation change, duplicate approval resolution, provider death with approval pending, output-envelope limits, inline/artifact threshold, artifact hash validation, unauthorized retrieval, path traversal, and interrupt during command execution.

## M5 — Codex-Owned Mission-Control Frontend

Codex must implement the frontend directly. Do not leave placeholder fixtures for a future Grok implementation pass.

### Functional screens

Implement the smallest production-quality set needed for Prototype 0:

- Mission Overview / session list
- Session Console
- session and runtime status header
- normalized event timeline
- message composer and Turn controls
- command/tool activity panel
- sticky Approval Dock
- file-change and diff review
- reconnect/offline/replay state
- clear `outcome_unknown` and lost-runtime recovery state
- system/error feedback sufficient to diagnose failures

### Session strip

Each session should communicate the important state in one scan, using real data only:

- provider
- model when available
- account profile
- project/cwd in a safe abbreviated form
- runtime/Turn state
- elapsed time
- token/usage information when available
- pending approval or error signal

Do not fabricate telemetry that the protocol does not provide.

### Timeline behavior

- use stable item identities
- preserve scroll anchors while deltas stream
- do not force auto-scroll when the operator is reading earlier content
- provide a clear return-to-latest action
- reconstruct authoritative completed messages after reconnect
- distinguish ephemeral live output from durable completed state
- avoid duplicate timeline entries after replay

### Approval UX

- use a sticky dock or stable panel rather than a modal that destroys reading position
- show action type, command or file-change summary, cwd, reason, expiry, and runtime context
- expose only valid actions for the current authoritative approval state
- refresh authoritative state before allowing a stale notification or restored tab to approve
- clearly display pending, approved, declined, expired, invalidated, lost-runtime, and conflict states
- never imply that a request succeeded before Core commits the resolution

### Diff UX

- support useful inline review for small diffs
- support artifact-backed retrieval for large diffs
- provide unified view and side-by-side view when practical
- show file list, additions, deletions, loading, integrity failure, authorization failure, and artifact expiry states
- keep large content out of WebSocket envelopes

### Visual direction

Use an aerospace mission-control visual language without copying proprietary logos, assets, or exact product designs.

Design principles:

- dense but readable information hierarchy
- dark neutral background with restrained contrast
- white/gray foundation with one primary accent
- reserve warning/error colors for real state
- monospace for paths, metrics, IDs, timestamps, and status labels
- minimal animation
- no decorative glow that reduces legibility
- no fake charts, fake metrics, or decorative telemetry
- consistent spacing and alignment
- clear desktop and mobile layouts
- approval and errors visible within one second

### Accessibility and responsive requirements

- keyboard-operable controls
- visible focus states
- semantic labels and landmarks
- sufficient contrast
- reduced-motion support
- screen-reader status announcements for important state changes
- desktop, narrow laptop, tablet, and mobile layouts
- touch targets suitable for approval on a phone
- no horizontal page overflow caused by command output or diffs

Use the existing normalized protocol and fixtures. Do not import provider adapters or database modules into the web application.
